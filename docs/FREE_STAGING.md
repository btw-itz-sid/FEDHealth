# Free staging on Render

Status: source configuration prepared; no public deployment has been created or verified yet. This is a research demo, not a clinically validated or always-on production service.

## What runs

One Docker web service serves the React build and Nest API from the same HTTPS origin. Its Python ML worker listens only on localhost. Neon persists accounts, assessments, experiments, dataset CSV bytes and trained model bytes. On startup the launcher runs migrations, ensures the initial administrator exists, starts Python, waits for its health endpoint, then starts the API and restores files before processing queued jobs.

This avoids losing uploaded datasets and ready models when Render replaces its ephemeral filesystem. Interrupted running jobs fail explicitly; queued jobs remain queued. Use one service instance only.

## Account setup and deployment

1. Create a Render account and sign in through GitHub. Account creation and acceptance of provider terms must be completed by the account owner. Do not share credentials in chat.
2. Create a **new empty Neon database/branch** for staging. Keep the development database separate. The initial migration deliberately refuses existing application tables.
3. Push the reviewed source, including `render.yaml` and `Dockerfile.staging`, to your repository. In Render choose New > Blueprint and connect that repository and branch. The blueprint requests the Free plan; check the displayed plan before creating the service.
4. Set these private environment values in Render: `DATABASE_URL` (Neon connection URL with TLS), `ADMIN_EMAIL`, and a unique `ADMIN_PASSWORD` of at least 12 characters and at most 72 UTF-8 bytes. JWT and ML service secrets are generated by the blueprint. Never put these values in Git or chat.
5. Deploy. The service uses Render's external URL for its allowed browser origin. No custom domain or paid service is required. The readiness URL is `/api/v1/health/ready`; it checks PostgreSQL and Python. Auto-deploy is disabled so reviewed releases can be deployed deliberately.
6. Sign in with the configured administrator account. In Account settings generate and securely save its recovery key. Create a separate personal account, then grant it researcher access from Administration if needed.
7. Upload an approved, de-identified PIMA-compatible CSV and train a model. A fresh database contains no local development accounts, datasets or trained pipelines. Assessments need a ready active model; no demonstration predictions are fabricated. Keep the benchmark holdout limitations documented in `MODEL_IMPROVEMENT.md`.
8. After confirming administrator recovery and login, remove `ADMIN_EMAIL` and `ADMIN_PASSWORD` from Render's environment and redeploy. Bootstrap skips creation when an active administrator already exists. If all admins are later deactivated, operator intervention is required.

## Acceptance checks before sharing a public link

- Open `/login`, `/register`, `/recover` and `/privacy` directly over HTTPS, including a page refresh. Unknown API URLs must return JSON 404, not the frontend page.
- Register a personal test account, save its recovery key, sign out and sign in. Verify the session cookie is Secure, HttpOnly, SameSite=Strict and scoped to `/api/v1`.
- Verify personal users cannot access researcher/admin endpoints, even by calling their URLs directly.
- Make one assessment with example data, verify saved history, then delete that history with password confirmation. Check another account's history remains untouched.
- Recover a disposable account with its saved key. Check the old password, old key and old session no longer work. Save the replacement key. Test personal account deletion using disposable records only.
- Train a small experiment and obtain a real prediction. Restart the service, then verify the same dataset, ready model, active-model selection and prediction remain available. Check queued/interrupted job behavior.
- Observe server memory during baseline training and FedAvg. If Render's free memory limit is exceeded, reduce training settings or move to a suitable paid server; do not describe an untested free deployment as reliable production.
- Let the service idle, then test its cold start and login again. Check error screens do not expose secrets or internal paths.

## Free-tier limits

Render currently suspends free web services after 15 minutes idle; wake-up can take about a minute. Local files are ephemeral, no persistent disk is available, and the free workspace allowance is shared between its services. See [Render free-service documentation](https://render.com/docs/free).

The application caps uploads at 5 MB, database dataset bytes at 25 MB total, each model at 10 MB and saved model bytes at 100 MB total. Training is limited to 2,000 rows in this profile. These are conservative application safeguards, not a guarantee that every training configuration fits the free server. History and audit tables also consume database storage; the operator must monitor Neon usage and maintain backups. See [Neon plans](https://neon.com/docs/introduction/plans).

Recovery uses a private one-time key because no email delivery service is configured. Email addresses are unverified sign-in identifiers. Losing both password and key prevents self-service recovery. Existing users can generate a key from Account settings after confirming their password.

Only public/example or synthetic measurements should be used. Do not collect identifiable patient records on this staging demo. The public Data & privacy page explains storage, recovery, account deletion and operator access.
